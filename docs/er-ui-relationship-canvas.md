# ER 关系画布第二阶段：纯文字实施规范

日期：2026-09-20。状态：本轮实施目标。

本文件面向无法识别图片的 Claude Code，完整描述用户所要求的界面。无需截图、图片识别或凭项目名字猜样式。

## 1. 本轮目标及与旧规范的关系

用户认为第一阶段成品与 ChartDB、drawDB 差别仍大。本轮主要参考 ChartDB 的紧凑表卡片和按关系组织的画布，结合 drawDB 清楚的字段端点、圆角折线及关系反馈。

关键目标是：用户能从某个字段沿线读到另一个表的具体字段；表的位置体现关联结构；可以拖动单张表调整布局。不能只改颜色、线宽和圆角后宣称完成。

本规范明确替代 `er-ui-redesign.md` 的这些限制：

| 第一阶段 | 本轮要求 |
| --- | --- |
| 固定列网格为主布局 | 自由世界坐标，已知关系驱动初始布局 |
| 关系只接表头中点 | 关系接实际字段，字段不可见时使用明确的汇总端口 |
| 禁止单节点拖动 | 支持拖动表头移动单张表 |
| 全部表同一细色条 | 少量统一调色板，按关系组件稳定分配，可保留现有用户颜色 |
| 只用中性端点 | 可靠元数据支持时展示基数，未知时保持中性 |

保留已实现的字段按需读取、共享缓存、二维虚拟化、短表自然高度、长表字段行虚拟化、主题切换及错误反馈。不要退回首字母分组、前 N 张截断或全库字段预加载。

本轮不加业务区域分组框、缩放、小地图、关系编辑、持久化布局或 D1–D9 模型。单节点坐标至少在当前标签生命周期内保留；现有工程已经支持的更长持久化能力可复用，不另起存储项目。

## 2. 目标画面的文字描述

### 2.1 整体构图

想象一个足够大的平面，上面分布大小不同的表卡片：每张卡片像紧凑的数据表，而不是大表单。卡片之间的空间用于关系连线；重要表在关联结构中占据自然位置，旁边分布引用它的表。不能将全部表按名称从左到右、从上到下铺成货架。

以实际存在下列关系的示例说明布局意图：

```text
addresses              orders              order_items
     ╲                 ╱                       │
       customers                               products

tags（若没有已知关系，单独放在外围）
```

这里只表达“关联近、孤立表在外围”，不是精确坐标或数据库特例。也允许形成从左到右 `customers → orders → order_items → products` 的层次。实现必须从真实关系计算，禁止识别这些表名后硬编码位置或补造关系。

两张表之间的连线从字段行侧边出发，先水平离开卡片，再通过圆角折线路径到达目标字段。字段名称、线的端点与路径高亮共同告诉用户“哪两个字段关联”。

### 2.2 背景与主题

- 浅色：接近白色、略灰的画布；卡片正文更亮，表头有轻微色差；正文深灰，类型次级灰。背景和卡片要能分辨，不能全部混成纯白。
- 暗色：较深画布、略亮表头、清楚的浅色正文；不要直接把浅色主题 RGB 反转。
- 点阵间隔约 20–24 个逻辑像素、直径约 1px，弱于普通连线。随世界坐标平移，仅绘制可见区域，不为每个点创建元素。
- 卡片可使用很轻的主题适配阴影，如果现有渲染支持且实测没有明显代价；默认依靠边框和底色区分，不使用大面积阴影。
- 初始内容四周至少 32px 留白。

## 3. 卡片排版：紧凑而清楚

### 3.1 尺寸基准

全部按 GPUI 逻辑像素；截图显示倍率不参与数值换算。

| 元素 | 首版目标 |
| --- | --- |
| 卡片宽 | 252px，集中定义，不按表名变化 |
| 圆角 | 约 6px，尽量复用现有 token |
| 边框 | 1px，浅色可见但弱于正文；选中轮廓约 2px，不改变内容布局 |
| 顶部色带 | 4px，贴合顶部圆角，不覆盖标题 |
| 表头高 | 30px，左右 padding 10px |
| 表名字号 | 12px semibold，左侧 14px 表图标 |
| 字段行高 | 22px，字号 11px，文字垂直居中 |
| 字段区上下 padding | 各 3px |
| 最多可见字段 | 8 行，多余内部滚动 |
| 长表页脚 | 20px，10–11px 次级文字 |

短表高度由真实行数决定。例如 3 字段卡片约 `4+30+6+3×22=106px`；8 字段约 216px；超过 8 字段约 236px（含页脚）。边框是否包含在外部尺寸中由一个共用几何函数处理，避免计算和绘制各自维护公式。

字段之间增加极淡的 1px 分隔线，仅在行之间出现；不能像电子表格那样画深色粗格线。线的绘制不得减少字段有效行高造成底部截字。

### 3.2 字段行横向结构

从左到右：`字段名称（弹性区域） | 约束图标槽 | 类型（右对齐）`。

- 左右各 10px padding。
- 普通字段名称使用正常文字色；已确认的外键字段名称可使用适中的主题强调色，不把所有类型都染成橙色。
- 名称与约束/类型区域间隔 6px；约束图标槽约 14px；类型列约 82px。
- 主键显示 key 图标；仅外键可显示 link 图标；同时 PK/FK 优先显示 key，tooltip 写明两者。
- 普通字段不放装饰性圆点。连线端口位于卡片边界，不占字段名布局宽度。
- 字段名称和类型分别省略，tooltip 给出完整限定表名、字段名、类型和已知约束。
- 类型颜色弱于字段名称；未知类型使用 `—` 或现有统一未知文案，不伪造类型。
- 可空信息只在确有元数据时出现在 tooltip；本轮不挤入更多约束列。
- 长表页脚显示 `1–8 / 18 个字段`，随滚动更新，范围必须与真实可见行一致。

### 3.3 颜色分配

- 定义约 5 个主题适配的低饱和色：蓝、青绿、紫、橙、玫红。全部通过 UiColors 或其统一调色板访问。
- 同一连通分量使用相同默认色，颜色帮助识别关联区域；大图颜色可以复用，不要求每张表唯一。
- 关系尚未就绪时用默认蓝色。就绪后一次性分配，之后不因 pan、render 顺序或新字段到达变色。
- 颜色只作辅助，不能代替关系线和文本。已有用户显式颜色优先。
- 本轮不增加颜色编辑器，不用随机数每帧分配颜色，不用数据库名字硬编码。

## 4. 字段级端口：本轮最重要的变化

### 4.1 可见字段

- 一条外键的源端连接 `from_table.from_column` 所在行的垂直中心；目标端连接 `to_table.to_column` 的行中心。
- 端口在卡片左右边界；左右侧由双方位置与路由决定，不固定“源永远在右侧”。
- 坐标必须使用节点世界坐标、表头高度、字段区 padding、真实字段顺序及滚动偏移计算。
- 节点内部滚动时，端口跟随字段移动；不能停留在原来的 y 坐标而误指另一字段。
- 端点显示约 4px 的小圆点，默认柔和、选中时强调。没有关系的字段不铺满无用途的圆点。
- 同一字段多关系允许共享锚点，路径在卡片外分开。

### 4.2 字段在内部视口之外

不得将离屏字段关系接到当前可见的第一行/最后一行并伪装为它的关系。

- 在字段滚动区上边缘/下边缘预留专用汇总端口，与真实字段端口有明显区别：小圆角标记，例如 `↑2` 或 `↓3`。方向应使用 AppIcon，数字是计数，不拿文本字符充当图标。
- 计数语义固定为隐藏且有关联的不同字段数；tooltip 再列出关联条目数和具体字段。双侧端口按实际侧别显示各自数量。
- 标记覆盖位置不能遮住字段文字、表头按钮、滚动条或页脚；必要时放在卡片外侧的小型标记区，并计入绘制/命中包围范围。
- 连接隐藏字段的边收敛到相应汇总端口，但各自关系身份保留。
- 点击汇总标记打开组件菜单，列出字段及关联目标；选择后将该字段滚入可见区域并高亮。只有一个字段时可直接定位。
- 字段重新进入视口后，关系恢复到实际行端口。更新只影响该表及邻接边，不重新布局全图。

### 4.3 字段尚未加载、找不到或加载失败

- 尚未加载时使用表头上明确的“字段待加载”汇总端口，这是临时状态，不能看起来像已经精确匹配。
- 不为获得所有端口而强制读取全库字段。屏外未加载端点可以使用该汇总几何位置；可见表按现有需求优先读取字段。
- 字段加载失败或关系引用字段不存在时保留关系，并以 tooltip/状态说明未解析原因；不得静默连接到同名近似字段。
- 区分卡片内部字段离屏和整张卡片在画布外。整张卡片离开画布不改变它的真实字段锚点，也不把端点吸到屏幕边缘。

## 5. 关系线、标记与选择

### 5.1 路径外观

- 普通线约 1.25px，必须明显比点阵深；选中/关联高亮约 2px。浅色可采用中灰语义 token，暗色采用可辨的灰蓝；数值由 UiColors 管理。
- 水平/垂直折线，拐角约 6–8px 圆角；端口外先留约 14px 水平短段，再转弯。已实现：底稿为「水平出→竖直降→水平进」正交线段，任何连续段都不得是斜线（回归：`(a_exit,a.y)→(b_enter,b.y)` 直连在 y 不同时产生斜线，已修复）。
- 相邻平行边用稳定的 6–8px 通道间隔。布局、滚动或拖动时路径应可预测，不随机换侧。
- 避开所有卡片正文和端点标签区域。使用空间查询获得附近障碍物，禁止逐边遍历全库所有节点。
- 预算用尽（间隙车道被障碍占用，例如阻塞卡与两端同 y 挡住走廊）：不得静默返回明显穿卡的单一兜底——改为有界外侧绕行：在两卡左右外侧若干车道 × 障碍上/下绕行带内（O(车道×带)×候选障碍，有界不无限搜索）逐条校验，命中首个合法折线即返回；全被占则返回碰撞最少的一条，绝不接受未评分的穿卡兜底。
- 自关联绕同一表外侧形成可见回路。相同两表不同字段/约束的关系保持独立，不能仅按表对合并。
- 密集图允许部分交叉，不承诺平面无交叉；选中时高亮路径帮助跟踪，不能靠静默删边解决密集问题。

### 5.2 基数与标签：不能复制图片里的数字而猜数据

参考图的端点旁有小圆形 `1 / N` 标签。只在现有元数据足以证明端点语义时显示；无证据的端点使用中性圆点，并在详情标明未知。

- 审查当前 `ErForeignKeyEdge`、Connector 外键/唯一约束元数据是否保留足够身份与约束信息。
- 不能因存在外键就一律画 `N:1`；源列可能有唯一约束，某些方言的引用端也存在特殊情况。
- 复合约束按完整有序列组判定唯一性，不能按单个字段、字段名字、`id` 后缀或 partial/conditional 索引猜测。
- 本轮不为了显示两个数字实施完整基数推断服务。现有信息不足则诚实保留中性端点，记录限制。
- 有效基数标签约 14px，紧靠端口外侧但不压到字段，字号 9–10px。不显示虚构的必选/可选乌鸦脚。
- 默认不在每条线中央铺满长外键名。hover/选中时显示关系名及 `源表.字段 → 目标表.字段`；显示用箭头可以是文本，操作图标仍用 AppIcon。
- 若原始模型把复合外键表示为多条字段配对，只能在可靠的约束身份内组合详情，不能跨表仅按约束名字合并。

### 5.3 高亮

- 选中表：表边框强调，直接邻接关系高亮；无关关系降低视觉强度但保留可辨性。
- hover/选中关系：高亮两端字段、路径和端点。端点字段被隐藏时，高亮对应汇总标记并可通过菜单定位。
- 点击空白或 Esc 取消选择；节点、关系、字段滚动区之间事件不能误穿透。
- hover 提示使用现有 tooltip；复杂关系详情可用项目已有浮层，外部点击/Esc 可关闭。

## 6. 从网格改为关系布局，同时维持稳定性

### 6.1 初始排布策略

- 以真实表关系建立邻接信息，按连通分量处理；孤立表也必须保留可达。
- 对有关系的组件使用确定性的分层布局：例如强连通分量压缩处理循环，再分层并用邻居排序减少交叉。先检查项目已有算法/依赖；无需引入 Web 布局框架。
- 被引用实体倾向放在左侧，引用它的实体向右展开；桥表、环、自关联要有明确处理，不无限递归。
- 关联组件内水平卡片间隔初始约 96px，垂直至少 40px；组件之间至少 96px，给连线留通道。
- 孤立表放在关联组件外围的紧凑区域，允许该区域使用网格，但不要让孤立表插入主要关系链。
- 不显示首字母分组入口、不折叠成隐藏分组、不限制可访问表数。
- 初始布局在后台执行，有代次保护及工作预算；UI 不执行全库力导向迭代或每帧重排。
- 复杂巨型组件若触发布局预算，返回合法、不重叠、可探索的确定性降级布局，并明确提示可重新排列；不得截断节点/关系或永远 loading。

### 6.2 分阶段加载时机

- 表目录先到而关系未到时，保留快速可操作的临时概览排列，并显示“关系加载中”。不能让首屏等待全库字段。
- 首次完整关系索引到达且用户尚未平移、拖动、选择、字段滚动时，允许一次后台关系布局应用。记录“已应用”，后续数据批次不再自动重排。
- 用户已经操作过，则保持现有坐标，显示“关系已就绪，可按关系排列”的轻量页面提示/按钮；用户点击后应用新布局。
- 部分关系失败时保持可用图，标明不完整；不要根据部分图宣称某表是永久孤立表。
- 重新排列不重读数据库、不清空字段缓存。
- 字段加载造成高度变化只影响卡片自身。初始排布为每张表保留最大卡片高度的碰撞包络，以避免后续加载与邻居重叠；包络不绘制外框，也不等于固定五列网格。
- 已加载短表仍收短。不能通过拖慢加载、隐藏所有普通字段或预读全库字段换取整齐。

### 6.3 用户坐标与重排

- 手动拖动后的节点标记为固定。普通刷新、关系补齐和局部展开保留其坐标。
- 新增表安排在邻居附近的空闲位置，不重新铺排已有节点。
- 工具栏“按关系排列”默认保留手动固定节点；需要重置时通过明确菜单项“重置手动位置并排列”，用户显式执行，提供现有撤销机制或至少一次恢复上次布局能力。
- “回到起点”改为回到布局的初始视口；不会清除人工坐标或数据缓存。
- 不在 resize、主题切换、内部字段滚动、普通 pan 时重排。

## 7. 单节点拖动与输入行为

- 按住表头非按钮区域拖动，只移动该表；超过约 4px 阈值才开始拖动，普通点击仍是选择。
- 拖动时光标按项目平台习惯呈现可抓取/正在抓取状态，选中轮廓清楚。不要让鼠标移动变成邻域展开请求。
- 连线端点和邻接路径实时跟随；不拖动关联表，不每帧更新全图坐标。
- 空白处拖动继续平移整张画布。字段区滚轮只滚字段；滚动条拖动只调滚动；表头菜单/展开按钮不开始节点拖动。
- 画布外释放、窗口失焦、切换或关闭标签清理拖动状态。不得要求鼠标回来再移动一次才能结束拖动。
- 拖动可使节点短暂重叠，用户坐标优先；不要释放后偷偷把节点弹回自动布局位置。
- 长表滚动位置、选择和固定节点状态使用稳定表身份保存，不能依赖布局向量下标。
- 局部 ER 的“展开关联”按钮保持原有功能，复用缓存；与表头选择/拖动明确区分。

## 8. 虚拟化、路由与分层实现要求

当前代码已拆为 `er/canvas.rs`、`er/scene.rs`、`er/node.rs`、`er/interaction.rs`；实施前以实际代码为准，不退回大单文件。

- 原来的按 y 排序固定行索引不再适用于任意拖动位置。采用适合自由矩形的空间查询结构，支持单节点更新和任意正负坐标；候选后精确测试真实卡片矩形。
- 大节点、长边不能按覆盖面积/距离无界复制索引项。先复用现有能力，选择有界存储策略并测量。
- 边索引按实际折线路径包围范围构建；两端屏外但路径穿过视口仍可见，不能继续只检测原始端点直线。
- 节点拖动、字段滚动时更新该节点端口及邻接边；路径缓存不能保留过期坐标。
- 用户拖动节点形成新障碍时，需让受影响的非邻接路径也能失效/重算。通过空间查询限定范围，可在拖动结束后做局部修正，不每帧重新路由全部关系。
- hover 命中测试也走候选查询，不能每次鼠标移动全量扫描所有节点、字段和边。
- 拖动更新尽量只通知画布；pan 未变化不重复 notify。使用现有独立实体能力，必要时完成画布独立 Entity，验证主窗口重绘次数。
- 纯拓扑布局、加载和后台协调位于 app 侧合适职责；UI 管理世界坐标投影、字段滚动、绘制与命中。核心类型不依赖 GPUI。
- 最小扩展元数据时保留 schema/表/约束身份和原始字段顺序；不得把 UI 查询 SQL 搬到渲染层。
- 不实施未确认的逻辑关系存储或 Agent 服务；视觉缺少元数据时明确未知即可。

## 9. 自动测试与实施阶段

按以下顺序推进，每步保证已有功能可用，不能最后只交付静态卡片样式：

1. 核查并记录现有行为/性能，调整紧凑卡片和主题调色板。
2. 建立字段端口投影、隐藏字段汇总端口与定位交互。
3. 实施自由坐标索引和表头单节点拖动，确保邻接线实时跟随。
4. 实施后台关系布局、一次性应用条件和手动固定坐标保护。
5. 完善路由、关系选择、hover 详情和可证明的基数标记。
6. 自动验证后请用户配合文字验收，按反馈修复。

必须覆盖的行为测试：

- 非首字段、不同字段顺序、同名跨 schema 表的端口定位。
- 字段滚动一整行和半行的锚点位置；上下隐藏字段汇总；重新可见后恢复真实端口。
- 未加载、加载失败、字段不存在、刷新字段减少/变零的安全行为。
- 复合外键的完整字段配对详情、同表自关联和同表对多条不同约束不丢失。
- 拖到负坐标后仍可见、可命中；旧位置不再误命中；只有受影响几何需要更新。
- 后台关系布局不得覆盖新拖动；首次关系到达只在用户未操作时自动应用一次。
- 环、桥表、多个组件、孤立表、稠密组件、全部无外键的布局确定性和有限非重叠坐标。
- 两端屏外的折线、端点直线不穿视口但真实绕行路径穿视口、路径索引更新。
- 折线全正交（无斜线段）；拖动第三张卡进 src↔dst 同 y 间隙后重路由且不穿该卡；真实 demo 链呈左→右层次、孤立表在外围、真实卡片矩形两两不相交。
- 长表字段行数量与真实视口匹配，不重复出现底部截字。
- 明暗主题切换后缓存失效；关闭标签清理任务/实体/输入状态。

按 AGENTS.md 执行 cargo fmt、cargo check、受影响模块测试。比较同构建配置、同视口、同数据下 50/200/1843/10000 表的表现，包含长表和大量关系；记录布局耗时、索引规模、可见元素数和实际查询工作量。布局/路由预算不能依赖“真实库应该只有少量长边”的假设。

基准探针 `er_probe_perf_scales`（desktop：`cargo test -p fluxdb-desktop er_probe_perf_scales -- --ignored --nocapture`）实测（纯 CPU，非 UI FPS）：链式大分量下，关系布局 50→~1ms / 200→~1.6ms / 1843→~18ms / 10000→~108ms（后台执行）；场景构建 0.4→18ms（后台）；本帧物化（网格 + 逐边路由）0.36→7.2ms，且每次 render 同步执行（`er_diagram_content` 与 `request_visible_columns` 各一次）——这是大库连续平移时已知的每帧热点，未做增量路由缓存；可见节点始终有界（本例 ≈5）。关系布局仅在建场景/「按关系排列」时后台运行，不随 pan 触发。

不把几何函数测试耗时当作 UI FPS；未达标时报告真实热点与限制，不承诺没有测过的 60/120 FPS。

## 10. 用户手动验收：仅文字，不截图

Claude Code 无法识别图片，不截图、不调用截图工具、不要求用户发送图片，也不宣称自己看过界面。先完成自动验证、必要日志，然后给用户准确启动方式及如下短清单：

1. 小库：表的位置是否体现关系链，不再只是固定三列/五列货架？无关系表是否仍可访问？
2. 找一条连接非首字段的关系，确认两端落在正确字段行；拖动这张表，线是否跟随？
3. 滚动长表让关联字段隐藏：是否出现上/下汇总标记；点标记能否定位字段；是否误指其他行？
4. hover/选中一条关系：是否清楚看到路径、两端字段、完整关系说明？未知基数是否保持未知？
5. 慢加载时先操作画布，关系加载完成后是否保持位置；手动排列后拖动某表，刷新是否保留？
6. 检查三字段短表、超过八字段长表、类型右对齐、行分隔和主题；滚动到底无截字。
7. 大库分别平移和拖动单表约 10 秒，反馈是否卡顿及 FPS/FRAME/P95 文字读数。
8. 画布外松开、切换标签、关闭标签，是否无残留拖动和异常？

用户回复“通过/失败+现象”即可。程序能读取的日志由实现者读取分析，不让用户重复整理。区分自动通过、用户通过和待验证；没有图片识别能力不阻碍实施，但不能伪造视觉验收结果。

## 11. 交付标准

完成定义：不是“卡片更像 ChartDB”，而是“字段关联可读、表按关系组织、节点可拖动，同时保留大库性能”。

同步更新 `er-design.md` 的实际实施记录，注明此阶段取代固定网格与表头端口；标明字段隐藏的汇总策略、未知基数限制、布局预算降级和未验证平台，不修改 D1–D9 审批状态。

若存在必须依赖用户选择或现有数据库接口缺失的阻碍，报告具体位置、已完成内容和最小缺口；不要用一个中性表头端口替代全部字段级关系然后宣布完成。
